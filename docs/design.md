# デッドマンスイッチ 要件・設計方針

最終更新: 2026-08-16

## 0. 登場人物

本書では以下の呼称を用いる。

| 呼称 | 意味 |
|---|---|
| 運用者 | この仕組みを自分自身に対して仕掛ける人。ハートビートの発信元であり、監視される対象でもある |
| 一次受信者 | 発火時に最初に通知を受け取る人。同居の家族など、運用者の異変に最も早く動ける立場を想定する |
| 二次受信者 | 一次受信者が同時に被災した場合に備えた並列の通知先。別居の家族など（本フェーズでは未実装） |

## 1. 目的

事故や急病で運用者が意識不明などの状態になった場合に、**2〜3日以内**に必要な情報が家族へ届くようにする。
明示的なチェックイン操作を必要とせず、普段の行動をそのまま生存シグナルとして利用する。

## 2. スコープ

### 対象

- ハートビート（生存シグナル）の収集と無音検知
- 無音時間に応じた段階的なエスカレーション
- 発火時の通知配信（初期の宛先は一次受信者ひとり）

### 対象外

- 緊急通報（119番等）との連携
- 医学的な意味での生存確認・バイタル監視
- 資産や契約の自動処理（法的に無効になり得るため、情報の引き渡しに限定する）

### 今回のフェーズ

ハートビートの仕組みを確立するところまで。二次受信者の追加、発火時に配信する内容の設計は次フェーズ。

## 3. 設計上の背骨

> **不発は許容しない。誤爆は許容する。**

この非対称性がすべての判断基準になる。迷ったら「壊れた時にどちらへ倒れるか」で選ぶ。
誤爆のコストは「一次受信者に無用な通知が1回飛ぶ」だけだが、不発のコストは仕組みの存在意義そのもの。

派生する原則:

- 閾値を保守的にして誤爆を減らすより、**リセットを簡単にして誤爆を無害化**する
- 「一時停止」の類は原則作らない。作る場合も自動復帰させる
- 動作確認を運用に組み込む。テストしていない通知経路は死んでいるものとみなす
- 想定外の入力は捨てずに運用者へ流す。沈黙は不発と区別がつかない

## 4. 要件

### 機能要件

| ID | 内容 |
|---|---|
| F-1 | 日常の端末操作を、追加の手間なしにハートビートとして送出する |
| F-2 | 無音が48h / 60h / 72h に達した時点で、それぞれ別のアクションを起こす |
| F-3 | 48h・60hの通知は運用者宛。技術的な内容のままで構わない |
| F-4 | 72hで一次受信者へ発火する。文面は人間が読んで理解できる日本語であること |
| F-5 | 通知を受けた後、任意の端末から発火を延期できること |

### 非機能要件

| ID | 内容 |
|---|---|
| N-1 | 判定・通知の基盤を運用者の自宅環境に置かない（運用者と一緒に停止するため） |
| N-2 | 自作コードを最小化する。既製のサービスで表現できる部分は自作しない |
| N-3 | 発火処理を差し替えても、ハートビート側に変更が波及しないこと |
| N-4 | 誤爆時に機微情報が漏れないこと（通知の中身に口座番号・証券番号等を含めない） |

## 5. ハートビートの定義

**画面ロック解除**を唯一のシグナルとする。

採用理由:

- 本人性が高い（家族が代行できない）
- 頻度が高く、旅行中でも途切れない
- 意識不明であれば確実にゼロになる

不採用としたもの:

| 候補 | 不採用の理由 |
|---|---|
| Googleアカウント無効化管理ツール | 最短3ヶ月で、必要な時間軸に対して遅すぎる |
| PC操作 / git commit / タスク消化 | 旅行や休暇で普通に途切れる |
| 家計簿・決済アプリの取引記録 | 家族カードでも発生するため本人性がない |
| 自宅サーバの稼働 | 運用者が居なくても動き続ける |
| バッテリー残量・通信状態 | 圏外や充電切れで誤爆する |
| 心拍・歩数（Health Connect） | 補助としては有効だが、端末紛失による誤爆を許容する方針のため今回は不要 |

## 6. アーキテクチャ

```
[Android / Tasker]
      |  ロック解除イベント → %LASTSEEN を更新（通信なし）
      |  毎時 → 直近1時間以内に解除があれば ping
      v
[healthchecks.io]  ... 無音検知・状態管理・エスカレーション
      |
      +-- alive-48 --> 運用者（Discord: 運用者用チャンネル）  ※標準通知をそのまま
      +-- alive-60 --> 運用者（メール）                       ※標準通知をそのまま
      +-- alive-72 --> Webhook --> [通知アダプタ] --> Discord（一次受信者 + 運用者）
```

自作するのは Tasker のタスク1個と、通知アダプタ1個のみ。
状態管理・タイマー・リセット処理は healthchecks.io に任せる。

### チェック定義

| 名前 | Period | Grace | 通知先 |
|---|---|---|---|
| `alive-48` | 48h | 1h | 運用者（Discord） |
| `alive-60` | 60h | 1h | 運用者（メール） |
| `alive-72` | 72h | 1h | Webhook → 通知アダプタ |

- period / grace は最大365日まで設定可能なため、この時間軸は問題ない
- ping が1回届けば3本とも同時にUPへ戻る。リセット処理を自作する必要はない
- 48hと60hの通知経路は**必ず別種にする**。無音の原因が端末故障だった場合、同じ端末へのプッシュを2回送っても届かないため、60h側はPCからでも受け取れる経路にする
- 通知に含まれる ping URL を任意の端末から叩けば、それが F-5 の延期操作になる

#### 72h の経路について

72h の配信先は Discord とするが、**48h で使う運用者用チャンネルとは別サーバ・別チャンネルの Webhook を用いる。**
これは宛先の分離であって、経路の冗長化ではない。48h と 72h は Discord というサービスに共通で依存しており、Discord 側の障害やアカウント失効は両方を同時に落とす。この単一障害点は次の2つで受け止める。

- 中段の 60h をメールにしてあるため、Discord が全滅していても運用者には届く
- 72h が一次受信者の手元まで実際に到達するかは、四半期ごとの実弾テストでしか確かめられない（§8）

### 端末側（Tasker）

```
プロファイル1: Event → Display → Display Unlocked
  Task: Variable Set %LASTSEEN = %TIMES        （通信を伴わない）

プロファイル2: Time → 毎時
  Task: IF (%TIMES - %LASTSEEN) < 3600
          HTTP Request GET https://hc-ping.com/<alive-48 の UUID>
          HTTP Request GET https://hc-ping.com/<alive-60 の UUID>
          HTTP Request GET https://hc-ping.com/<alive-72 の UUID>
```

**イベントと送信を分離する**のが要点。解除時に圏外であっても、次の毎時実行が拾い直す。

**時刻トリガーで無条件に ping してはいけない。** 条件式を省くと、端末が机に放置されていても ping が飛び続け、永久に発火しない状態になる。この設計における唯一かつ最大の設定ミス。導入時に必ず「条件を満たさない状態では ping が飛ばないこと」を実測で確認する（`docs/setup.md` Step 7-②）。

### 通知アダプタ

healthchecks.io の Webhook 連携は、`$NAME` `$STATUS` 等を埋め込んだ任意のJSONをPOSTでき、リクエストヘッダも指定できる。これを受ける小さなエンドポイントを1つ用意する。

- 配置先: Cloudflare Workers など、運用者の自宅から独立した場所（N-1）
- 契約: `POST /hook` + 共有シークレット（healthchecks側のカスタムヘッダで付与）
- 責務: イベント種別を見て、宛先とテンプレートの対応表を引き、整形して送るだけ
- 状態は持たない。判定ロジックも持たない

この形にしておけば、発火時のアクションを差し替えるときも、変更範囲はアダプタ内部の対応表だけで済む（N-3）。宛先の追加も同様。

アダプタの挙動で、§3の原則から直接導かれるもの:

- **未知のイベント名を捨てない。** 対応表に無いイベントが来た場合、無視せずフォールバック宛先（運用者）へ生のペイロードごと転送する。設定ミスやサービス側の仕様変更を、沈黙ではなく通知として観測できるようにするため
- **受け口を緩くする。** ペイロードのキー名は `event` を正とするが、見つからなければ `name` / `check` も見る。キー名の食い違いで沈黙するくらいなら、緩く受けて拾う
- **72h発火は一次受信者と運用者の両方へ同時に送る。** 運用者が生きていれば誤爆に即座に気づき、ping URL を叩いて取り消せる（F-5）
- **配信に失敗したらフォールバック宛先へ通知した上でエラーを返す。** healthchecks 側に失敗が記録され、後から追跡できる

実装は `worker/` を参照。

## 7. 失敗モードと扱い

### 誤爆（生きているのに発火する）— 許容

| 原因 | 対処 |
|---|---|
| 48時間以上の連続オフライン | 国内利用では実質発生しない。長期の海外渡航時のみ留意 |
| バッテリー最適化による Tasker の停止 | 省電力の対象外に指定。メーカー独自の省電力も個別解除 |
| 端末の故障・紛失 | 対処しない（許容する方針） |

### 不発（発火すべき時に動かない）— 許容しない

| 原因 | 対処 |
|---|---|
| 毎時 ping の条件式漏れ | 導入時に「端末を放置してチェックがDOWNになるか」を実際に確認する |
| 通知経路の失効（Webhook失効、迷惑メール判定） | 四半期ごとの実弾テスト |
| チェックの一時停止のまま放置 | 停止中でも ping を受ければ自動再開する設定のまま使う |
| healthchecks.io 側の障害・アカウント失効 | 月次サマリーメールの受信を確認する |
| アダプタが未知イベントを黙って捨てる | フォールバック転送で必ず可視化する（§6） |
| 機種変更後、旧端末が ping を送り続ける | 運用者が動いていなくてもUPのままになる。移行時に旧端末のプロファイルを無効化する |

## 8. 運用

- **導入直後2週間はドライラン。** 通知先を運用者だけにして、実際の最長無操作時間の分布を確認する。48/60/72 の妥当性はその実データを見てから確定する
- **四半期ごとに実弾テスト。** 閾値を一時的に数分へ縮め、一次受信者の手元まで通知が届くことを確認する
- **年1回、インフラの棚卸し。** 課金カードの有効期限切れでサービスが止まると不発に直結する

手順は `docs/setup.md` の付録にまとめてある。

## 9. 今後の検討事項

- 二次受信者の追加（一次受信者が同時に被災するケースを想定し、別居の家族などを並列で入れる必要がある）
- 発火時に配信する内容の具体化。口座番号・証券番号等は含めず「どこに何があるか」「誰に連絡すべきか」に留める方針までは決定済み
- 実物の保管場所と、そこへのアクセス手段の受け渡し方法（パスワードマネージャの緊急アクセス機能の利用を検討）
- 資産・契約に関わる部分は自動化の対象外とし、遺言や死後事務委任契約など別枠で検討する
